这里的每个 ```bash 围栏是一条可执行判据，`forge change verify` 会按出现顺序编号（#1、#2……）并依次实跑。`tasks.md` 里引用的就是这个序号。

- 一个围栏 = 一次 shell 调用（```bash 用 `bash -c`，```sh 用 `sh -c`），可以写多行；**每行写一条命令**，多步就多行。
- 不要用 `&&` 串联：`set -e` 不会因为 `a && b` 里 a 失败而退出（AND-list 是条件上下文），后面再跟一行就把整段跑成 0——这是最常见的假绿写法，verify 会直接拒绝。
- 围栏内以 `set -eo pipefail` 执行（sh 围栏只有 `set -e`；本机没有 sh 时 ```sh 围栏回落 bash，证据里记的是实际用的壳）。
- verify 会**直接拒绝**这些写法（不是只写在文档里）：管道 `|`、`||`、后台 `&`、
  `set +e`/`set +o errexit`、`eval`、再调用一层 shell（`bash -c`、`bash -lc`、
  `/bin/sh -c`、`bash.exe -c`、用 `${IFS}` 拼参数都算），以及条件/循环/取反/包装
  （`if`、`for`、`while`、`case`、`!`、`command`、`exec`、`source`、`trap`）、
  命令替换（反引号、`$( )`）、行尾反斜杠续行。它们都能把失败变成 0，等于假绿。
  需要保留输出就写进文件；确实需要多步逻辑时，把它写进仓库里的脚本再调用，
  脚本自己 `set -e` 并把失败以非零退出码传出来——verify 看不到脚本内部，
  脚本吞掉的失败它无从判断。
- 引号里的同类字符是字面量（如 `echo "a||b"`），`#` 之后的注释也不算代码，都不会被误杀。
- 会拦的包装：`env`/`timeout`/`sudo -u x`/`nice`/`xargs`/`find -exec` 里再开一层 shell、`{ ... }` 分组、`$( )`/反引号、行尾续行、`true`/`:`/`exit 0` 及 `/usr/bin/true` 这类占位。
- **不拦**：仓库脚本内部（`bash check.sh` 里的写法）、变量拼出来的命令、`ssh host cmd` 这类隔着进程的间接执行。verify 只证明命令跑过、退出码是 0；判据有没有真在检验东西，由 review 看判据本身。
- 只写 `true` / `:` / `exit 0` 的围栏会被拒绝：它必然成功，等于没判据。
- 首个非零即停，后面的命令记为 skipped；每条都 0 才封印（摘要里写 `sealed: true`、但 checks 里有非零退出码的不算，verify 会逐条核对）。
- 列表项里的缩进围栏也是判据；只有 HTML 注释 `<!-- -->` 里的围栏才当示例跳过。
- 失败的证据别删：删掉最新那份，列表会回到上一次封印，看起来像"一直是通过的"。
- 命令在仓库根目录执行；单条超时 10 分钟；单条输出最多保留 2 MiB（超出写截断标记）。
- 四份产物（proposal/design/tasks/acceptance）必须在、都删掉 `forge:fill` 标记，且至少有一条真会执行的命令，否则 verify 直接拒绝——acceptance 是判据，另外三份是它的审计线索（内容是否充实靠 review 看，不靠机器猜）。
