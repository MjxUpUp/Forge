# 专项分析：复发低分维度 scope×57 / efficiency×39（2026-09-22）

> 状态：分析完成，产品改进已实施（health 低分维度分布直方图 + 形态判读，随本计划落地）。
> 数据源：`forge act list --json` 全量 113 个任务结论（2026-08-17 ~ 2026-09-22）。

## 结论一句话

**两个维度都是量纲/任务粒度信号，不是纪律缺口**——但 `forge health` 只输出
"×N 频次"，读起来像纪律崩坏，诱发"沉淀拆任务铁律"这类数据不支持的假规则。
修复：分布直方图 + 形态判读进 health 输出（已实施）。

## 数据

### scope（分档：≤50 行=100 / ≤200=80 / ≤500=60 / >500=40；低分 = <70）

| 档 | 任务数 |
|---|---|
| 100（≤50 行） | 31 |
| 80（≤200 行） | 25 |
| 60（201–500 行） | 26 |
| 40（>500 行） | **31** |
| 70（中性，diff 不可用） | **0** |

- 低分 57 个：26 个在 201–500 行、31 个超 500 行源码（测试文件已排除）。
- **46/57 低分任务总分仍 A 级**（其他维度抵消）；1 个 C。
- 低分 refs 全是功能火车级工作（dsh-plugin、zcode-support、task-convergence、
  trust-profile……），非返工/救火类。
- 无时间趋势：2026-08 低分 30/58、2026-09 低分 27/55——稳定 ~50%。

### efficiency（分档：≤15min=100 / ≤30=90 / ≤60=75 / ≤120=55 / >120=35）

| 档 | 任务数 |
|---|---|
| 100 | 14 |
| 90 | 32 |
| 75 | 28 |
| 55（60–120min） | 22 |
| 35（>120min） | 17 |

- 低分 39 个（>60min 活跃跨度）；30/39 仍 A 级。
- 活跃跨度含质量协议仪式本身：审查子代理运行、门禁串行、验收重跑——这些是
  **设计内的成本**（本 session 内门禁至少拦下 4 次真实错误），不是浪费。
- 该维度阈值曾按 dogfood 数据校准过一次（evaluator.go 注释：旧阈值把 80% 真实
  任务压在 40-60、无区分度）。

## 判读框架（已固化进 `forge health` 输出）

- **跨全档分布（含 ≥80 分样本）** → 量纲/粒度信号：分档阈值与任务现实脱节，
  先校准分档或审视任务拆分粒度；
- **集中低档** → 纪律缺口：优先沉淀守卫/铁律。

scope 与 efficiency 均属前者。

## 为何不落"拆任务铁律"（负结论）

数据不支持硬规则：低分不拉低交付质量（46/57 A 级、全过审查门）、31 个 >500 行
任务多为内在耦合的功能火车（拆分有真实协议开销：每任务 proposal/spec/门禁/
审查一遍）。强行立规会产生两类伤害：假规则稀释铁律信噪比；诱发为分拆而拆的
机械拆分。若未来某维度转**集中低档**形态，再按缺口处置。

## 产品决策候选（未实施，待后续按需取用）

1. scope 分档 per-project 基线化：以项目滚动中位任务规模定档，替代全局绝对行数
  ——改动面大（评分器语义），需独立提案；
2. efficiency 活跃跨度剔除子代理等待：SendMessage/后台任务等待期是否计入
  activeSpan 需先核实 toollog 口径——若计入，协议仪式时间被重复计价；
3. 低分维度的 RetrospectiveNudge 文案带形态判读（当前 nudge 只提维度名）。
