# 发布说明模板

## 变量列表

**必填**：
- `version`：版本号 + 发布日期
- `user_visible`：用户可感知变化（最多三条，价值先行——用户关心"我能做什么新事情/什么问题被修了"，不关心内部重构）
- `upgrade`：升级方式与破坏性变更（有 breaking 必须首条）

**选填**：
- `fixes`：缺陷修复（每条关联 issue）
- `internals`：内部改进（对用户不可见但值得记录的：性能、安全）
- `links`：完整 changelog / 发布公告链接

## 章节结构

```
# 发布 | {version}

## 用户可感知变化

{user_visible；每条一行：能做什么新事情 / 什么问题被修了。
超过三条说明该拆版本或合并同类项——条目越多单条注意力越少}

## 升级须知

{upgrade；含破坏性变更与迁移步骤，无则写"无破坏性变更，常规升级即可"}

## 修复与内部改进

{fixes + internals；修复关联 issue 编号，内部改进一句话}

{links}
```

## 风格示例

> # 发布 | v1.42.0
>
> ## 用户可感知变化
>
> - 文档产物新增 L1 可读性检查：`forge docs lint` 一键扫描空转措辞与无证据结论
> - complete 前自动校验文档回检证据，漏检任务被拒并给出修复指引
> - 修复：Windows 路径含中文时 hook 间歇失效（#789）
>
> ## 升级须知
>
> 无破坏性变更，常规升级即可。

价值先行三条以内、破坏性变更最前、修复带编号——不罗列 commit 流水，不写内部术语给外部用户。
