# 技术方案模板（三档）

先定档位，再填模板。档位按**风险**定，不按代码行数：

| 档位 | 什么时候用 | 要写什么 |
|---|---|---|
| 直接改 `none` | 一句话能说清的改动；标准变更（纯文档、依赖 patch 升级、配置值） | 不写方案，只写验收命令 |
| 小方案 `mini` | 跨 3 个以上目录、做法有多种可选、改不熟悉的代码、引入新依赖 | 下方单文件骨架，≤150 行正文 |
| 完整方案 `full` | 改 schema/迁移、公共接口/契约、鉴权；跨团队、不可逆或安全/数据敏感 | 需求/设计/任务三文件（章节分配见骨架下方），每文件 ≤400 行正文，人工批准 |

开工时声明档位；宿主提供路径硬触发器（迁移/schema/接口契约/鉴权/依赖/跨 3 个以上目录）时，推导档位更高则取较高者，下调须写明理由。拿不准就上调一档。
## 变量列表

**必填（mini/full）**：
- `tldr`：≤120 字——决策 + 需要读者做什么（批准/给反馈/知会）
- `problem`：要解决的问题（一句话 + 现状证据 file:line / 数据）；目标可量化；全文每个事实或性能断言都带指针
- `non_goals`：本可以做但这次不做的事（不是「不会崩溃」这类否定句）
- `requirements`：功能需求 `REQ-n` 写清触发与响应（「当 X 时，系统 Y」）；非功能需求 `NFR-n` 写数字（p99 ≤ 200ms，不写「要快」）；每条配 `accept[REQ-n]: <cmd> :: <expected>`
- `touchpoints`：要改的文件与符号（`path:Symbol`），计划新建的写 `new: path`，新依赖写 `new-dep: 模块@版本`——宿主支持时登记后即成为计划改动范围，实改超出报「方案外改动」
- `alternatives`：至少 2 个备选，其中一个是「什么都不做」，压成对比表
- `verification`：端到端验证与回滚（accept 围栏）
**选填**：
- `interfaces`：接口/契约，用代码块（Go 类型、proto、JSON Schema），不用散文重新定义
- `dataflow`：Mermaid 图，每条边标注同步/异步与协议
- `invariants`：`INV-n` 不变量，硬约束注明由哪个测试/hook 执行
- `risky_steps`：高危步骤（迁移/删除/鉴权/外部调用），集中列在一起
- `open_questions`：未决问题；有阻断项时不进入实现

## 骨架（mini 单文件；full 三文件：需求文件 = TL;DR + 问题与目标 + Non-goals + 需求与验收 + Open Questions；设计文件 = 设计 + 备选对比 + 风险；任务文件 = 任务列表（每项回链 REQ-n）+ 验证与回滚）

## 写作约束（对人和对 agent 同时成立）
- **短**：正文超出档位上限就拆成「索引 + 子文档」；agent 能从代码读到的不写（不做代码库导览、不逐文件描述）
- **规范性语句只写一次**：其余位置按 ID（REQ-n / INV-n）引用，不重复改写
- **约束在前、验证在后**：TL;DR、Non-goals、需求放前面，验证与回滚放最后
- **写完核查引用**：方案点名的路径、行号、符号、模块逐条确认真实存在（宿主提供方案核查命令时直接用它）

## 风格示例
> ## TL;DR
> 采用门禁前移：complete 前挂 deterministic pre-flight（复用 acceptance 快照机制），不引入新流程概念。请批准方向。
>
> ## 备选对比
> | 方案 | 一句话描述 | 结论 |
> |---|---|---|
> | 门禁前移（推荐） | complete 前校验 | — |
> | Stop hook 拦截 | 会话结束才拦 | 否：反馈太晚，修复成本已沉淀 |
> | 什么都不做 | 继续靠 advisory | 否：提醒转化率 <50%（{数据链接}），改变不了行为 |
