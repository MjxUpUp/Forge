# 对抗性验证双协议

两个共享同一精神的协议：**被检验方的自述不可信，必须有独立于被检验方的证据源**。协议 A 用于观点/结论层（辩论），协议 B 用于交付层（验收）。共同的敌人是确认偏误——agent（和人）在"被印证"的快感里会批量产出自我肯定。

## 协议 A：红蓝对抗辩论（锚外部证据）

**Iron Law：辩论的每个论点必须引用外部独立源（官方文档 / 论文 / 源码 / 官方 API），禁止基于模型自身权重自辩驳。**

### 为什么这么硬

真实事故：用户问"你的辩论是否引用了外部资料作背书"，答"全都基于模型本身权重"——自我辩驳没有意义，结论只是采样噪声。另一事故：单份奉承源（厂商材料）触发确认偏误，15 分钟产出 5 条自我肯定全被推翻。教训沉淀为三条判据：

1. **无外部源的论点 = 未验证假设**，必须显式标记，不得进入结论段。
2. **单一奉承源不可采信**：被检方自己写的宣传材料不算独立证据；出现"被印证"快感时强制换独立源重验。
3. **强措辞配强标准**：结论用"证实/推翻"级词汇时，证据必须是可核查引用，不是"感觉上对"。

### 流程

1. 立论方产出论点清单（每条：主张 + 当前证据状态）。
2. 红队逐条攻击：优先攻击**引用最弱**的论点；攻击本身也须锚外部源（否则标记为"风格性质疑"降权）。
3. 裁决：每条论点三态——证实（有独立源）/ 推翻（有反证）/ 未验证（无外部源）。未验证论点如实报告，不硬凑结论。
4. 打稻草人检查：红队开药方前必须先证明自己读过被批评的对象（源码/文档），"没读代码开药方"是历史事故第一大来源。

## 协议 B：对抗性验收（防假绿）

**Iron Law：验收结论必须来自逐功能点的实际执行 + 严格比对，禁止"文档比对式验收"。**

### 为什么这么硬

真实事故：agent 按设计文档逐条比对后宣布验收通过，用户驳斥"很多功能是断裂的"，第二轮严格比对才暴露——文档说有 ≠ 代码能用。同构事故：声明式 pass（声称审过但没真审）放行了问题代码。

### 流程

1. **列验收点清单**：从需求/设计文档提取可执行验收点（每条必须是能跑的动作，不是"已实现 X"的描述）。
2. **逐点实跑**：每个验收点实际执行（跑命令 / 发请求 / 点界面），记录原始输出。跑不了 = FAIL，不是 SKIP。
3. **断裂扫描**：单点通过 ≠ 链路通过——补集成点检查（A 的输出是 B 的输入的接缝处），这是"每个功能看着都对、连起来全断"的藏身处。
4. **严格比对**：预期 vs 实际逐字比对，宽容匹配（"差不多一致"）一律降级为 FAIL。
5. **裁决**：全过 = PASS；任一 FAIL → 列断裂清单回修，**修完必须整体重验**（修复的副作用第一轮看不到）。
6. **双路径一致性检查**：同一判定存在两条执行路径时（快路径/兜底），验证两路径共用单一真相源——路径各自实现是假绿温床（判定漂移后一条绿一条红，快路径先跑就永远绿）。

## 决策树

- 检验对象是**观点/结论/调研报告** → 协议 A。
- 检验对象是**交付物/功能** → 协议 B。
- 两者都要（大决策 + 大交付）→ 先 B 后 A：先确认事实层，再辩论观点层。
- 时间紧 → 协议 B 的逐点实跑不可裁剪；协议 A 可降为"最弱论点抽查 3 条"。

## 执行后自查清单

- [ ] 协议 A：结论段零"未验证假设"未标记项；每条证实论点有可核查引用
- [ ] 协议 A：红队开药方前读过被批评对象本身
- [ ] 协议 B：验收点 100% 实跑，零"看起来对"项
- [ ] 协议 B：集成断裂扫描执行过
- [ ] 协议 B：修复后整体重验（非只验修复点）
- [ ] 双判定路径共用单一真相源

## Gotchas（真实事故库）

| 坑 | 现象 | 解决 |
|---|---|---|
| 权重自辩驳 | 辩论热闹但全是采样噪声 | Iron Law：无外部源 = 未验证假设 |
| 单源奉承 | 一份厂商材料"印证"全部结论 | 独立源强制 + "被印证"快感是警报信号 |
| 文档比对假绿 | 文档说有就打勾 | 逐点实跑 + 原始输出 |
| 打稻草人 | 红队批评的不是真实设计 | 开药方前先引被批评对象原文 |
| 修复后不复验 | 修复引入新问题直接放行 | 修完整体重验 |
| 双路径漂移 | 快路径恒绿掩盖兜底路径已坏 | 单一真相源 helper |

## 与其他 skill 的分工

- **code-review-gate**：diff 级代码质量审查；本 skill 管观点层与交付层验证，不审代码风格。
- **project-acceptance**：常规验收流程；本 skill 协议 B 是其对抗档（adversarial mode），用户点名"严格/深度/防假绿"时用本 skill。
- **research-workflow**：调研主流程；本 skill 协议 A 是其结论段的红队检验步骤。
- **research-workflow Phase L**：单点轻量事实核查；多点对抗性检验用本 skill。
- **verification-driver**：驱动外部工具做端到端验证的操作方法；本 skill 协议 B 定义"验证要多严"的标准，前者是执行手段。
