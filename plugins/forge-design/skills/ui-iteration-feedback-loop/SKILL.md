# UI 迭代决策点反馈环

前端多轮打磨的交互协议：把"改一版→用户看→再说哪里不对"的模糊循环，变成**结构化的决策点交付 + 编号反馈映射**。源自真实迭代：用户对 UI 的反馈天然是编号列表（"1.漏掉的补上 2.颜色不对全是暗色 3.决策1=B、决策2=C"），agent 端必须用同样结构承接，而不是挑几条顺手的改。

## 核心原则

- **决策前置**：拿不准的审美/交互选择不在交付后等用户骂，交付时就把选项摆出来（决策N = A/B/C + 一句推荐理由），用户批量回选，一轮顶三轮。
- **零静默丢弃**：编号反馈每条必须有处置记录（done / skipped+理由 / 拆到下轮），丢了哪条用户一定会在下轮发现。
- **双主题交付**：涉及颜色的改动默认给 light/dark 两版——"颜色不对全是暗色"类返工的本质是主题上下文没对齐。

## 交付协议（每次出 UI 时的固定动作）

1. **改动清单**：本次改了什么、动到哪些文件/组件。
2. **决策点列表**（≤5 个，超过就拆轮次）：

   ```
   决策1 导航栏收起方式：A 图标收起（推荐，省空间） / B 完全隐藏 / C 不收起
   决策2 卡片圆角：A 8px（跟现设计系统） / B 12px 更柔和
   ```

3. **双主题变体**：颜色/对比相关改动附 light 与 dark 两版（截图或说明均可），标明当前默认。
4. **已知未做**：本轮明确不做的和原因——主动说比被发现强。

## 反馈处理协议（收到编号反馈时）

1. **逐条解析**：每条编号意见 → 意图分类：

   | 反馈形态 | 分类 | 处置 |
   |---|---|---|
   | "1.颜色不对…" | 修正 | 改，回贴改动点 |
   | "决策1=B" | 回选 | 应用选项 B，标 done |
   | "2.再加个筛选" | 新需求 | 评估范围：小→本轮做；大→拆下轮并说明 |
   | "3.这个不用了" | 撤销 | 移除，确认影响面 |

2. **处置表回执**：反馈处理后回一张表——`#1 done（改动点）/ #2 拆下轮（理由）/ #3 skipped（理由）`。skipped 必须有理由，没有理由的 skip 就是静默丢弃。
3. **新决策点**：本轮处理中冒出的新选择 → 进下一份决策点列表，不现场猜。

## 决策树

- 用户反馈带编号 → 走反馈处理协议，先出处置表再动手。
- 用户反馈无编号但多点 → 先整理成编号清单回执确认（"我理解为 3 点：…，对吗"），确认后同上。
- 用户只回选决策码（"全按推荐" / "决策1=B 其余A"）→ 应用后回变更摘要，不需要再确认。
- 涉及信息架构/大改（不是样式打磨）→ 转 prototype-confirmation 先确认方向，本 skill 管样式与细节迭代层。

## 执行后自查清单

- [ ] 交付含决策点列表（≤5）且每项有推荐
- [ ] 颜色相关改动给了双主题
- [ ] 上一轮编号反馈每条有处置记录（含 skip 理由）
- [ ] 无"已知未做"藏着没说
- [ ] 新冒出的选择进了新决策点而不是暗自决定

## Gotchas（真实踩坑）

| 坑 | 现象 | 解决 |
|---|---|---|
| 颜色不对"全是暗色" | 只在一套主题下看效果 | 双主题交付成默认动作 |
| 反馈被选择性处理 | 用户下轮发现某条没理 | 处置表回执，零静默丢弃 |
| 决策点一次给十几个 | 用户回选疲劳，反而全跳过 | ≤5 个，超过拆轮次 |
| 暗自决定本该问的 | 交付后被打回"谁让你这么改的" | 拿不准 = 决策点，不猜 |
| 编号反馈夹新需求 | 当修正顺手做，范围失控 | 分类表区分修正/新需求，新需求评估再入轮 |

## 与其他 skill 的分工

- **prototype-confirmation**：方向/信息架构层的原型确认；本 skill 管其下的样式与细节迭代。
- **frontend-aesthetics-execution**：审美执行的 token/风格方法论；本 skill 管交互协议（何时给选项、如何接反馈），不管怎么配色。
- **frontend-feature-development**：组件编码规范；本 skill 不管代码怎么写。
- **design-audit**：设计文档 vs 代码的落地审计；本 skill 管迭代过程，不管落地率核查。
