# 方案脱离实际的案例

## 案例 1：没看模型就出 ChatML 方案

**场景**: 项目需要设计 prompt 格式与本地模型交互。
**做了什么**: 基于 Qwen 系列模型通常支持 Hermes ChatML 格式的行业知识，直接出了 ChatML 格式的 prompt 工程方案。
**实际**: 测试发现推理引擎（llama.cpp）的 `tool_calls` 字段永远返回 None，模型根本不支持工具调用。ChatML 格式的方案完全脱离现实。
**代价**: 浪费了一轮讨论时间，方案从零重新设计。
**教训**: 先调一次 API 验证能力，再设计格式。

## 案例 2：凭猜测使用 calamine crate

**场景**: 项目需要解析 Excel 文件。
**做了什么**: 不查文档直接写 `calamine::Reader::new()`，泛型参数凭直觉填。
**实际**: calamine 的 API 需要指定 Reader 类型（Xlsx、Xls 等），构造方式完全不同。
**代价**: 反复编译失败 3-4 轮。
**教训**: 使用新依赖前，先 `cargo doc --no-deps -p calamine` 或读源码。

## 案例 3：没有基准的优化方案

**场景**: 讨论项目性能优化。
**做了什么**: 提议加缓存层、加连接池等优化。
**实际**: 当前连基本功能都没跑通，性能瓶颈完全未知。
**教训**: 没有 profile 数据的优化方案是空中楼阁。

## 案例 4：用了不存在的类型变体

**场景**: 项目错误处理。
**做了什么**: 使用 `CoreError::ToolExecution`，编译失败。
**实际**: 实际变体名是 `ToolExecutionFailed { tool, message }`。
**代价**: 编译失败后才知道。
**教训**: 使用项目内自定义类型前，先 grep 确认变体名和字段名。

## 案例 5：假设目标浏览器支持现代 API（前端）

**场景**: 给内网管理系统加批量复制功能。
**做了什么**: 基于"现代浏览器都支持"的常识，方案直接用 `navigator.clipboard.writeText()` + `structuredClone()`。
**实际**: 目标环境是内网旧版 Chrome（HTTP 非安全上下文，`navigator.clipboard` 为 undefined；`structuredClone` 在该版本不存在），功能上线即白屏报错。
**代价**: 紧急回滚 + 用 `document.execCommand` 降级方案重写。
**教训**: 浏览器 API 方案先查 caniuse 并在目标 webview/浏览器实测，"现代浏览器都支持"不等于"用户的环境支持"。

## 案例 6：按新版标准库出方案，项目锁在旧工具链（Go）

**场景**: Go 项目要加 HTTP 路由。
**做了什么**: 推荐用 Go 1.22 `http.ServeMux` 的模式匹配（`mux.HandleFunc("GET /users/{id}", ...)`），称"标准库就能做，不用引路由库"。
**实际**: 项目 `go.mod` 锁在 Go 1.20 且因内部基建原因暂不能升级，`ServeMux` 模式匹配语法编译直接报错。
**代价**: 方案推翻，重新评估是否引 chi/gorilla。
**教训**: 推荐"标准库新特性"前，先看 `go.mod` 的工具链版本——语言新特性的可用性由项目实际版本决定。

## 案例 7：给单机环境开 Kubernetes 处方（基础设施）

**场景**: 内部工具访问量上涨，讨论扩容方案。
**做了什么**: 按行业惯例推荐"上 K8s + HPA 自动扩缩容 + Ingress 灰度"。
**实际**: 部署环境是客户内网的单机 docker-compose，无外网、无 K8s 集群、且客户安全规范禁止引入集群编排；真实瓶颈只是 SQLite 单文件锁。
**代价**: 方案讨论浪费一轮，最终用"换 PostgreSQL + compose 里加一行 replicas"解决。
**教训**: 基础设施方案先确认目标运行环境（单机/集群/有无外网/合规约束），再谈架构模式。
