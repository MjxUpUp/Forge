# 领域建模（领域语言治理）

在设计讨论中**主动**构建和打磨项目的领域模型：挑战术语、用边界场景压力测试、在术语敲定的当下就地写进 `CONTEXT.md`。

> **边界**：仅仅*读* `CONTEXT.md` 对齐词汇不算本 skill——那是任何 skill 都该有的单行习惯。本 skill 管的是**改变**模型的时刻，不是消费模型的时刻。

## 核心价值

共享语言是复利资产：

- **对抗用词漂移**：会话越长 agent 用词越发散、同一概念三个名字——术语表是把用词钉住的锚
- **表达收敛**：agent 不再用 20 个词说 1 个词的事（"lesson 落盘拿到文件系统位置" → "materialization cascade"）
- **命名一致**：变量/函数/文件按术语表命名，代码库对 agent 更可导航

## 五条纪律

### 1. 对照术语表挑战

用户用的词与 `CONTEXT.md` 现有语言冲突时，**当场**指出，不要默默选一边：

> "术语表里 cancellation 定义为 X，但你刚才的用法像 Y——是哪个？"

### 2. 收敛模糊语言

用户用模糊或超载的词时，提议一个精确的规范词：

> "你说'账号'——是指 Customer 还是 User？这是两个不同的东西。"

### 3. 用具体场景压力测试

讨论领域关系时，发明探测边界的场景，逼用户对概念边界精确表态。不要停在抽象共识上——"订单能部分取消吗？取消后已开发票怎么办？"这类场景才能暴露模型漏洞。

### 4. 与代码互相印证

用户陈述"系统是这样工作的"时，核对代码是否同意。发现矛盾就暴露：

> "代码里取消的是整个 Order，但你刚说可以部分取消——哪个是对的？"

### 5. 就地更新，不攒批

术语敲定的**当下**更新 `CONTEXT.md`。不要想着"等讨论完一起写"——攒批 = 丢失。格式见 [references/CONTEXT-FORMAT.md](references/CONTEXT-FORMAT.md)。

## 文件结构

- **单 context（多数仓库）**：根目录一个 `CONTEXT.md`
- **多 context**：根目录 `CONTEXT-MAP.md` 做索引，指向各 context 自己的 `CONTEXT.md`（详见 references）
- **懒创建**：没有 `CONTEXT.md` 就在第一个术语敲定时创建；没有 `docs/adr/` 就在第一个 ADR 需要时创建。不为结构而结构

## CONTEXT.md 的边界（硬约束）

`CONTEXT.md` 是**术语表，且只是术语表**：

- ✅ 收：本项目特有的领域概念（定义是什么，不定义做什么）
- ❌ 不收：实现细节、规格说明、临时草稿、通用编程概念（timeout/错误类型/工具模式——项目用得再多也不收）

收录前自问：**这个概念是本 context 特有的，还是通用编程概念？** 只有前者属于术语表。

## ADR 联动

讨论中决策 crystallize 时，**三个条件全满足**才提议记 ADR：

1. **难逆转**——以后改主意的代价是实打实的
2. **无上下文会困惑**——未来读者会纳闷"当初为什么这么做"
3. **有真实权衡**——存在过真正的备选方案，且基于具体理由做了选择

缺任何一个就不记。真要记时，走 `architecture-decision-record` skill 的模板和流程，本 skill 不重复 ADR 格式。

## Gotchas

- **问题**：讨论很顺畅，术语表一直没建 → **现象**：会话越长 agent 用词越发散，同一概念三个名字 → **解决**：第一个术语敲定的当下就建文件，懒创建不等于不创建
- **问题**：把 CONTEXT.md 当笔记本 → **现象**：塞满实现细节和 TODO，术语淹没在噪音里 → **解决**：硬约束只收术语；实现决策去 ADR，任务状态去 forge task
- **问题**：术语表建完就腐化 → **现象**：代码改名了术语表没跟 → **解决**：纪律 4（与代码互相印证）是防腐机制，发现漂移就地修
- **问题**：多 context 仓库把所有词塞进根 CONTEXT.md → **现象**：billing 的词和 ordering 的词互相污染 → **解决**：出现第二个内聚词簇时引入 CONTEXT-MAP.md，不要提前拆分

- [ ] 每个术语定义 ≤ 2 句，说的是"是什么"而非"做什么"
