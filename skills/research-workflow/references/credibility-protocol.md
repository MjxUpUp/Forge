## 为什么要这一层

2026-10 对本机 23 次深度调研的复盘（31 条承重断言回原文核验）：0 捏造、0 死链，但 10% 不支持、23% 只部分支持。失真全部发生在 dive → report → 下游文档的转述链上：删掉原文 hedge、丢掉场景限定、两篇来源拼成一个新结论。学界定位一致——deep research 终稿错误 84.7% 产生在编排/写作层（arXiv 2608.24306）。另外三类问题：「高信度」按 worker 数而非独立来源数计（循环互证）；答了相邻问题；把外部结论直接写成本地可做的建议。

本协议的原则：**能脚本化的交给 `scripts/research-lint.sh`，不能脚本化的交给隔离上下文的子代理，散文规则只留给判断题。**

## 1. 研究契约 brief.md（开搜前）

建 run_dir 后第一个文件。字段：

```markdown
# Brief
- 原问题（用户原文，逐字）：
- 要服务的决策（这份调研要帮谁决定什么）：
- 子问题（编号 Q1..Qn，每个可独立判定答完没答完）：
- 范围内 / 范围外：
- 时间窗（死线）：
- 什么算答完（每个子问题的出口条件）：
- 已知线索（含本机旧报告——只当线索，见第 2 节）：
```

- **深度档开搜前把 brief 给用户确认**（一条消息：子问题 + 范围 + 时间窗，问"按这个查？"）。用户已在请求里写清全部字段时可跳过确认，在 status.json 记 `brief_confirmed: "implicit"`。
- 每个 worker 的 spawn prompt **重注入原问题原文 + 本 worker 对应的子问题编号**（防长程目标漂移）。
- 维度切分、insight、报告每一节都必须挂回至少一个子问题。挂不上的发现写 `{run_dir}/parking.md`，不进报告正文。
- 报告开头先逐个子问题给结论（答完 / 部分答 / 查不到），再展开。

**防的失败**：用户问"是不是真需求"，报告论证"问题存在"——答了相邻问题。

## 2. 来源族与信度判定

**来源族（source family）**：追溯到同一原始出处的一组来源算一个族。下列都算同族：

- 同一 URL（不管被几个 worker 引用）
- 转载、聚合、二手报道追到同一原始出处
- 共作者论文、同一团队的系列文章
- 同一厂商的博客 + 文档 + 新闻稿 + 社媒
- **本机旧调研报告与它引用的来源**——旧报告只能当线索，引用前必须回到它的一手源；旧报告本身不是证据

**信度四档**（verify.md 用这套，取代"几个 worker 撞到"）：

| 档 | 标准 |
|---|---|
| 高 | ≥2 个独立来源族一致；或 1 个一手权威源（官方文档/论文原文/政府原文）且已检索反证未发现 |
| 中 | 1 个一手权威源，反证未检索或检索不充分；或 ≥2 个独立二手族一致 |
| 低 | 单一二手源、博客、厂商自报数据、搜索摘要（未打开原文） |
| 矛盾 | 独立来源族在同一指标/时间/定义上分歧 |

- **单一来源族永远不是高**。verify.md 每条高信度必须列出它的来源族（族名 + 代表 URL）。
- 厂商自报数字（ARR、benchmark、用户数）最高到中，并标"厂商自报"。

**防的失败**：同一 README 被两个 worker 抓到判高；同一条 HN 数据算两路；共作者论文算独立。

## 3. 限定条件随断言传递

dive 的 Key Evidence 表多一列「限定」：场景、样本、模型、时间、原文 hedge 词（perhaps / may / preliminary / in setting X / 仅限 Y）。

规则：

- 原文有 hedge 或场景限定的，**report 与任何下游文档必须保留**；没有就写"无"。
- **摘要/TL;DR 不得比正文更强**：正文写"可能相关"，TL;DR 不能写"导致"。
- 两个来源各说一半时，不得合成一个两个来源都没说过的结论；要写就分开写、各挂各的引用。

**防的失败**：METR 原文 "perhaps because…" 在 TL;DR 变成"作弊率反升 43 倍"；"仅 ChatDev 场景"在下游消失；IFScale 的指令条数与 ETH 的文件长度被拼成"上下文越长越差"。

## 4. 反证检索（全模式）

- 每个维度 worker 的 Mission 必含反证检索：用反向措辞（批评 / 失败 / 局限 / 反例 / does not / fails to）至少检索 2 次。
- dive 的 Tensions 段写明反证检索式；查无反证时写「已检索未发现：<检索式>」，不得留空。
- 反框架 worker（scan_anti）不再只限撒网模式：锁定与文件增强模式也派 1 个，不给 map.md context，任务是挑战主流 framing。
- insight 每条的「反例/边界」字段为空时，同样写「已检索未发现：<检索式>」。

**防的失败**：引一篇论文论证"提示层禁令无效"，却漏掉同一论文里 prompt 把作弊率从 92% 降到 1% 的数据。

## 5. 承重断言独立核验 claims.md（写报告前）

**承重断言** = 会进 TL;DR、结论、建议的断言，以及报告里所有数字、日期、引语。

步骤：

1. 主 agent 从报告草稿抽承重断言，写 `{run_dir}/claims.md`：

   ```markdown
   | ID | 断言 | 限定 | 引用 | 原文 quote | URL |
   |---|---|---|---|---|---|
   | C1 | 审查阶段占 59.4% token | 仅 ChatDev + GPT-5，30 任务，初步结果 | [^12^] | "...59.4% of tokens..." | https://... |
   ```

2. spawn **新上下文的核验子代理**（不 fork 当前会话），prompt 只给 claims.md 的 ID、断言、限定、URL——**不给草稿、不给推理过程、不给 quote**（让它自己从原文找）。它逐条打开 URL，判定：
   - 支持：原文明确支持断言与限定
   - 部分支持：方向对但数字/范围/限定有出入（写明出入）
   - 不支持：原文没说或说的相反
   - 不可达：403/超时/付费墙（写明尝试了什么）
3. 核验结果写回 claims.md 的「核验」列，并汇总到 verify.md。
4. 处置：不支持 → 删或改写；部分支持 → 按原文收窄措辞；不可达 → 降一档信度并在报告标注。
5. 数量多时分批派多个核验子代理（每个 ≤15 条），同一波并行。

**报告只能引用已核验的承重断言**。写作时新增的链接、数字，必须补进 claims.md 并核验后才能写入。

**防的失败**：写作层临时加料、把转述当原文引号、日期错位半年。

## 6. 本地适用性核验（建议类结论）

报告里任何「建议我们做 X」「X 可以直接用」，必须二选一：

- 附本地证据：本机记录（checklog、历史任务、日志）、代码位置、实测命令输出；
- 或明确标注「外部推断，未经本地验证」，并给出本地验证需要看什么数据。

"外部已证明"只证明外部场景成立。需要论证可行性时转 evidence-based-proposal。

**防的失败**：报告标"✅ 已证明、现在就可以做"的两条建议，用本机记录一查被推翻。

## 7. 运行状态 status.json 与检索日志 search_log.md

`{run_dir}/status.json`（主 agent 维护，每个阶段结束更新）：

```json
{
  "topic": "agent-memory",
  "mode": "locked",
  "tier": "standard",
  "brief_confirmed": "user",
  "stage": "delivered",
  "degradations": [
    {"what": "dimension D4 worker failed", "why": "429 after 3 retries", "impact": "D4 evidence only from scan"}
  ],
  "searches": 74,
  "fetches": 61,
  "claims_checked": 23,
  "downstream": ["docs/surveys/2026-10-agent-memory.md"]
}
```

- `mode` ∈ `scatter` / `locked` / `file-only` / `file-augmented`；`stage` ∈ `brief` / `scan` / `dive` / `verify` / `claims` / `report` / `delivered` / `abandoned`。
- **禁止静默降级**：跳过任何步骤（verify、反证、claims 核验、维度不足、worker 失败）都写进 `degradations`，并在交付消息里告诉用户。
- `searches` / `fetches` 取自 `{run_dir}/search_log.md` 的实际行数，不用估算。每个 worker 把自己的检索追加进 search_log.md：`| worker | 时间 | 工具 | 查询或 URL | 纳入/排除 | 理由 |`。
- 会话中途结束时，把 `stage` 停在实际到达的位置；下次接续先读 status.json。

**防的失败**：报告自报搜索量比实测虚高 23–60%；5/13 个 run 有缺口却没有任何文件说明停在哪、为什么。

## 8. 停止规则（替代搜索量下限）

按复杂度分档定投入，出口看"答完没有"，不看搜了多少次：

| 档 | 场景 | 维度 worker | 每 worker 工具调用 |
|---|---|---|---|
| 轻 | 单个对比、单一主体的现状 | 3–4 | 10–20 |
| 标准 | 方向调研、竞品格局 | 5–7 | 15–25 |
| 深 | 开放集合、跨领域、要支撑重大决策 | 7–9 + 撒网 | 15–30 |

出口条件（全部满足才进写作）：

- 每个子问题有 ≥2 个独立来源族支撑的结论，**或**明确写「查不到」并给出已尝试的检索式；
- 每个核心结论做过反证检索；
- 矛盾点已消解或标为领域真实分歧。

"查不到 / 信息不足"是合法结论，不要为了凑满而降低来源标准。

## 9. 交付前 lint

交付前跑：

```bash
bash <skill 目录>/scripts/research-lint.sh <run_dir>
```

检查必备文件、status.json 字段、报告引用与 URL、claims.md 核验列与数字一致性、内部标签泄漏。有 ERROR 不交付，先修；WARN 在交付消息里说明。可选 `--check-urls` 实测 URL 可达（需要网络，较慢）。
