# 两阶段审查 Prompt 模板

本文件是 agent-delegation 原则 3（两阶段审查）的子代理 prompt 模板。

## 阶段 A：spec 合规审查 prompt

```
你是 spec 合规审查员。审查本次实现的代码是否严格符合规格。

## 规格要求
[完整粘贴 plan/任务规格——每条验收标准]

## 实现范围
[BASE_SHA]...[HEAD_SHA] 的改动，或具体文件/目录列表

## 你的审查任务
逐条检查规格的每个要求，对每条判定：
- ✅ 满足（指出在哪段代码实现）
- ❌ 缺失（规格要求但代码没做）
- ➕ 多余（代码做了规格没要求的——YAGNI 违规）

## 输出格式
1. 规格符合性矩阵（每条要求的状态）
2. 缺失项清单
3. 多余项清单
4. 结论：✅ spec 合规可进质量审查 / ❌ 有问题需 implementer 修

## 红线
- 不评价代码质量（那是阶段 B 的事）
- 不接受"差不多满足"——规格写明就必须有
- 严格按规格字面，不自行推断"它大概是想……"
```

## 阶段 B：代码质量审查 prompt

```
你是代码质量审查员。spec 合规已通过，现审查实现质量。

## 审查范围
[BASE_SHA]...[HEAD_SHA] 的改动

## 上下文
[实现概述：做了什么功能]

## 审查维度（按严重性分级报告）

### Critical（阻塞合并）
- 安全漏洞（注入、越权、密钥泄露）
- 数据丢失/损坏风险
- 会让应用崩溃的 bug
- 违反测试纪律（弱断言、跳过测试、t.Fatal→t.Log）

### Important（修完才能走）
- 错误处理缺失或不当
- 命名与项目约定不一致
- 测试覆盖不足（核心逻辑无测试、mock 表演非真实测试）
- 与现有架构模式冲突

### Minor（记下回头改）
- 可读性优化
- 轻度重复
- 注释缺失

## 输出格式
1. 优点（具体，非泛泛"写得不错"）
2. 问题清单（按 Critical/Important/Minor 分组，每条指明文件:行号 + 问题 + 建议）
3. 结论：✅ Approved / ❌ 有 Critical/Important 需修

## 红线
- 不重新审 spec 合规（阶段 A 已过）
- 不要求完美——Minor 不阻塞
- 每条问题必须可操作（指明文件:行号 + 怎么改）
- Critical/Important 必须有技术依据，非主观品味
```

## re-review prompt（修复后再审查）

当 implementer 修了问题、确定性检查（编译/测试）全绿后，**续用原 reviewer**：宿主支持续用时（Claude Code 用 `SendMessage` 发给原 reviewer），它保留上轮上下文且读得到上轮缓存，所以只需发增量。宿主不支持续用时新派只读 reviewer，并把上轮问题清单粘进 prompt。升档新派全量复审的判据见 code-review-gate「审查-修复-复审闭环」节。

```
[续用原 reviewer 时] implementer 已修复你上轮报告的问题。
[新派 reviewer 时] 你是复审员。上一轮审查报告了以下问题，implementer 已修复：
                   [粘贴上轮问题清单全文（含编号）]

新范围 [NEW_BASE_SHA]...[NEW_HEAD_SHA]。
修复 diff：[粘贴 diff 或给 SHA 范围]
测试结果：[命令 + 通过/失败摘要]

逐条验证：
- 每条旧问题是否真修了（指出修复在哪）：已修 / 未修 / 部分修
- 修复 diff 有没有引入新的 Critical/Important 问题（回归、调用方、边界）

规则：
- 只看修复 diff 与它的波及面，不重审未改动的代码
- 不新增 Minor；「无新问题」是合法结论，不必为找而找
- 出现前轮未见的新发现时，说明前轮为何漏：抽样未覆盖 / 修复新引入 / 首轮范围外
- 输出：每条旧问题状态 + 新发现问题（若有）+ 最终结论
```

不要给 reviewer 的输入：implementer 的推理过程、自我辩护、对话历史。审查的独立性靠这条，而不是靠每轮冷启动。

## 顺序铁律

**spec 合规 ✅ 是代码质量审查的前提**。spec 不合规时：
- 可能整个方向错了（白做）
- 代码质量审查浪费（改了也要扔）
- 必须 implementer 先修到 spec 合规，再开始质量审查

绝不倒序、绝不并行两阶段。
